# clash-royale-battle-analyzer 要件定義書

- **バージョン**: v1.12.0
- **作成日**: 2026-09-05
- **対象**: クラッシュロワイヤルの対戦履歴を蓄積し、勝率および苦手カード・苦手デッキを分析するローカルツール

---

## 1. 目的

クラッシュロワイヤルの対戦成績を客観的なデータとして蓄積し、以下を明らかにすることを目的とする。

1. 自分の勝率が、どのカード・どのデッキを相手にしたときに落ちるのか（苦手の特定）
2. 自分が使っているデッキごとに、相性の良し悪しがどう変わるのか
3. 負けの原因が「実力」なのか「カードレベル差」なのかの切り分け
4. 現在の対戦環境（メタ）で何が流行しているのか

最終的なゴールは、感覚ではなくデータに基づいてデッキ選択と練習方針を決められるようにすること。

---

## 2. 技術的制約（設計の前提）

本ツールの設計は、以下の外部制約によって規定される。実装方針の大半はこの制約から導かれている。

### 2.1 対戦履歴は「直近25戦」しか取得できない

Supercell公式APIの `battlelog` エンドポイントは、**直近の数十戦分しか返さない**。それより古い対戦は永久に取得できない。

実測（2026-09-05、本ツールの対象アカウント）では **30件**が返却され、期間にして約5日分であった。公式ドキュメント上は25件とされることが多いが、実際の件数は変動しうるため、**件数を固定値として前提にしない実装とする**。

**帰結:**

- 過去の履歴を遡って一括インポートすることは原理的に不可能。
- 分析対象になるのは「本ツールの運用を開始した日以降」の対戦のみ。
- **定期的にAPIを叩いてローカルDBへ蓄積していく方式が必須**となる。
- 収集間隔が空きすぎると、その間に26戦以上プレイした分は取りこぼす。

### 2.2 APIトークンはIPアドレスに紐づく

トークン発行時に、アクセス元のグローバルIPアドレスを登録する必要がある。登録外のIPからのリクエストは 403 で拒否される。家庭用回線はIPが変動しうるため、直接アクセス方式では突然全機能が停止する。

**対策:** RoyaleAPIが提供する公式プロキシ `proxy.royaleapi.dev` を経由する。トークンには固定IP `45.79.218.79`（プロキシ側のIP）を登録するため、自宅のIPが変わっても影響を受けない。

### 2.3 カードレベルはレアリティごとに異なるスケールで返る

APIの `level` フィールドは、**そのレアリティの開始レベルを1として数え直した相対値**であり、ゲーム内の表示レベルとは一致しない。レアリティごとに開始レベルが異なるためズレが生じる（例: ゲーム内レベル11のレジェンダリーは `level: 3` として返る）。そのままの値で平均を取ると、レジェンダリーやチャンピオンを多く積んだデッキほどレベルが低いと誤判定される。

**検証済み**: 実測でカードマスタから導出したゲーム最大レベルは **16** であった。14を固定値としていた場合、レベル15・16のカードを扱えず集計が破綻していたことになる。

**対策:** 正規化式 `表示レベル = level + (ゲーム最大レベル - maxLevel)` により、全レアリティをゲーム内表示と同じスケールへ揃えてから集計する。

**ゲーム最大レベルは定数で埋め込まず、カードマスタから毎回導出する。** ノーマルカードの `maxLevel` は常にゲーム内最大レベルと一致するため、`全カードのmaxLevelの最大値` を採用すればよい。これによりアップデートで最大レベルが引き上げられても、カードマスタを再取得するだけで自動的に追随する。

### 2.4 プロキシ経由の通信にはUser-Agentの設定が必須

`proxy.royaleapi.dev` の前段にはCloudflareが設置されており、**既定のUser-Agentのままではリクエストが遮断される**。

実測では、Pythonの `urllib` が自動付与する `Python-urllib/3.12` が Cloudflare Error 1010（`browser_signature_banned`）で拒否された。認証エラーではないため、応答本文を見ないとトークンの不備と誤診しやすい。

**対策:** すべてのAPIリクエストに、クライアントを明示するUser-Agentを設定する。

```
User-Agent: clash-royale-battle-analyzer/1.0.0
```

エラーハンドリングでは、403応答のうち `error_code` が 1010 のものをトークン不正と区別し、User-Agentの問題として案内する。

### 2.5 その他

- battlelogの反映には数分の遅延がある。直後の対戦がすぐ現れるとは限らない。
- APIから返るカード名は英語のみ。日本語表示には自前の対応表が必要。

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| プレイヤータグ | `#XXXXXXXX` 形式のプレイヤー固有ID |

## 4. 全体構成

```
[Supercell公式API]
        |
        | HTTPS（proxy.royaleapi.dev 経由）
        v
[収集スクリプト collect.py]  <-- Windowsタスクスケジューラが1時間おきに起動
        |
        | 差分をUPSERT
        v
[SQLite データベース data/battles.db]
        |
        | 集計クエリ
        v
[分析モジュール analysis/]
        |
        v
[Flask Webダッシュボード app.py]  <-- ブラウザ http://127.0.0.1:5000
```

収集と閲覧は完全に分離する。収集は無人で動き続け、ダッシュボードは見たいときだけ起動する。

#### 日本語名の対応表

日本語名は公式APIから取得できないため、`src/data/card_names_ja.json` として同梱する。

- **キーはカードID**とする。英語名はリネームされうるがカードIDは不変であり、`cards.card_id` でそのまま結合できるため
- 形式: `{ "26000000": { "en": "Knight", "ja": "ナイト" } }`。`en` は人間が読んで検証・編集するために併記する
- 日本語名が対応表に存在しない場合は**英語名をそのまま表示**し、未対応カードとしてログに記録する（集計は正常に継続する）
- 初期データの典拠はクラロワ攻略Wiki（`wikiwiki.jp/c-r/Cards`）。APIのレアリティ別枚数との一致を検算に用いた
- 公式APIは言語指定に対応していない（`Accept-Language: ja` / `?language=ja` / `?locale=ja_JP` のいずれも英語名を返すことを実測で確認）

**保守方針**: ゲームアップデートで新カードが追加された場合、対応表JSONの手動編集が必要になる。画面上からの編集機能や略称エイリアス検索は本バージョンでは実装しない。手順は README に記載する。

## 8. 分析ロジック仕様

### 8.1 勝敗の判定

`crowns > opponent_crowns` なら win、`<` なら loss、同数なら draw。既定では draw を勝率計算の母数から除外する（設定で変更可能）。

### 8.1.1 集計対象の判定

対戦は種別を問わずすべてDBへ記録するが、勝率の集計対象は次の条件を満たすものに限る。

1. `battle_type` が集計対象の許可リストに含まれること（既定: `PvP`（ラダー）と `pathOfLegend`（ランク戦））
2. **`deckSelection` が `collection` であること**

条件2は、デッキを自分で組んでいない対戦を除外するためのもの。イベント戦にはドラフト形式（`draftCompetitive`）のものがあり、実測でも `type: "trail"` / `gameMode: "Chaos_1v1_TripleDraft"` の対戦が該当した。これらを自デッキ別分析に含めると、使っていないデッキの成績が混入する。

モード名の許可リストだけで判定すると、新規イベントの追加時に取りこぼす。`deckSelection` による判定を併用することで、未知のモードが追加されても自動的に正しく除外される。

**未知の `battle_type` が出現した場合も、記録は行いログに残す。** 集計対象に加えるかは後から設定で判断できるようにする。

### 8.2 カードレベルの正規化

APIの `level` はレアリティごとに基準が異なるため、そのままでは比較できない。次式でゲーム内表示レベルへ変換する。

```
ゲーム最大レベル = max(全カードの max_level)      ... カードマスタから導出
normalized_level = level + (ゲーム最大レベル - max_level)
```

ゲーム最大レベルが16の場合、レアリティごとの対応は次のようになる。

| レアリティ | ゲーム内の開始レベル | API `max_level` | API `level` の範囲 | 変換後 |
|---|---|---|---|---|
| ノーマル | 1 | 16 | 1〜16 | `level + 0` |
| レア | 3 | 14 | 1〜14 | `level + 2` |
| エピック | 6 | 11 | 1〜11 | `level + 5` |
| レジェンダリー | 9 | 8 | 1〜8 | `level + 8` |
| チャンピオン | 11 | 6 | 1〜6 | `level + 10` |

**ゲーム最大レベルは定数として埋め込まない。** ノーマルカードの `max_level` は常にゲーム内最大レベルと一致するため、カードマスタ全体の `max_level` の最大値を採用する。これによりアップデートで最大レベルが引き上げられても、カードマスタの再取得のみで追随でき、集計値が頭打ちにならない。

デッキの平均正規化レベルを自陣・敵陣それぞれで算出し、その差を `level_diff` とする。

**実装時の検証**: `doctor.py` に、自分の手持ちカードの正規化レベルを一覧表示する機能を設ける。ゲーム内の表示と突き合わせ、変換式が正しいことを実データで確認する。エボリューションやタワートループが別スケールで返る可能性もあるため、この照合は必須とする。

### 8.3 相手カード別勝率

各対戦について、相手デッキ8枚それぞれに対して1件ずつ「そのカードと対戦した」記録を計上する。

- `n` = そのカードが相手デッキに含まれていた対戦数
- `win_rate` = そのうち勝った割合
- `出現率` = `n` ÷ 総対戦数
- `勝率デルタ` = `win_rate` − 全体勝率

**苦手カードランキングは勝率デルタの昇順**で表示する。

> **解釈上の注意（画面にも注記する）**
> カード単位の勝率は「そのカードのせいで負けた」ことを意味しない。強いデッキによく採用されるカードは、それ自体が強いかどうかと無関係に勝率が下がって見える（交絡）。あくまで傾向を掴むための指標として扱う。

### 8.4 デッキの類似度グループ化

1. 自分の使用デッキをデッキハッシュ単位で集計する。
2. 使用回数の多い順に走査し、まだどのグループにも属さないデッキを新規グループの代表とする。
3. 代表デッキとカードが `しきい値` 枚以上一致する未所属デッキを、そのグループに吸収する。
4. しきい値の既定は **8枚中6枚**（設定で変更可能）。

グループ化は逐次的に行うと処理順序に結果が依存するため、**集計実行時に全デッキを対象として毎回まとめて再計算する**。これにより結果が安定する。

### 8.5 Wilson信頼区間（95%）

単純な `wins / n` は試合数が少ないとき極端な値になる。Wilson score interval により区間を求める（z = 1.96）。

```
center = (p + z²/(2n)) / (1 + z²/n)
margin = z * sqrt( p(1-p)/n + z²/(4n²) ) / (1 + z²/n)
```

表示例: `勝率 38.1% (±9.2%, n=42)`

### 8.6 最低試合数による区別

試合数が最低試合数（既定20）未満のレコードは、数値をグレー表示し「参考値」バッジを付ける。行自体は非表示にせず、データが貯まっていく過程が見えるようにする。

### 8.7 レベル差別勝率

`level_diff` を次の帯に分類し、帯ごとの勝率を算出する。

~~`-2.0以下` / `-2.0〜-0.5` / `-0.5〜+0.5`（互角） / `+0.5〜+2.0` / `+2.0以上`~~

**v1.6.0 で変更**: 上記の固定帯は実データの分布と合わず両端が常に空だったため、
0.5刻みでデータのある区分だけを並べる方式へ改めた。

互角帯の勝率が全体勝率より明確に低い場合、負けの主因はレベル差ではなく実力・相性であると解釈できる。

### v1.7.0 で変更した内容

- **レベル分析を折れ線グラフへ変更**し、刻みを 0.5 → **0.25** に細かくした
  - `level_diff` は必ず 0.125 の倍数のため、0.125 が最小の刻みになる
  - 細かくしてもデータ量・処理量は増えない（保存済みの値を振り分けるだけ）。

  - そのため実測値とは別に**傾向線**を重ねた。前後 `level_trend_window` の

  - 実測値の点の大きさを対戦数に比例させ、根拠の薄い点が見分けられるようにした

### v1.8.0 で変更した内容

- **レベル差と勝率の関係をロジスティック回帰で数式化した**（`src/analysis/levels.py`）

      P(勝ち) = 1 / (1 + exp(-(a + b × レベル差)))

  - 勝敗は2値・レベル差は連続値なので、この形が素直に対応する。
    直線で当てはめると勝率が0〜100%の外へ出てしまうため使えない
  - 係数はニュートン法（反復再重み付け最小二乗と等価）で求める。
    外部ライブラリは使わず標準ライブラリのみで実装している
  - 逆ヘッセ行列を係数の分散共分散として扱い、**95%信頼区間の帯**を描く。
    帯が広い部分はその付近の対戦が少なく、推定が定まっていないことを意味する
  - 当てはまりの良さは **McFadden の擬似決定係数**で示す。実測では 7〜8% 程度で、
    レベル差だけでは勝敗の1割も説明できないことがはっきり分かる
  - 係数の有意性は z 値（b / 標準誤差）で判定する
  - 曲線は**実データのある範囲だけ**を描く。範囲外は根拠が無く外挿になるため
  - 引き分けは勝ちとも負けとも言えないため、当てはめから除く
  - 試合数が `FIT_MIN_MATCHES`（20）未満、全勝・全敗、レベル差が一定の場合は
    当てはめが発散するのでモデルを出さない
- **傾向線を廃止した**。推定曲線が同じ役割（ばらつきをならして傾向を示す）を
  より根拠のある形で果たすため。これに伴い `level_trend_window` は**未使用**になった
  （設定ファイルには互換のため残している）
- グラフを**カテゴリ軸から数値軸へ変更**した。実測の点と推定曲線を
  同じ座標系に載せる必要があるため。区分が飛んでいても間隔が正しく空く

> 曲線の傾きは「レベルを上げれば勝率がこれだけ上がる」ことを保証しない。
> レベルを上げた時期と上達した時期は重なりやすく、傾きには上達の効果も混ざっている。

### v1.9.0 で追加した内容

- **カードの性能値表示**（`src/api/cardstats.py`、`src/analysis/cardstats.py`、`/card/<id>`）
  - HP・ダメージ・秒間ダメージ・射程・移動速度・展開時間・攻撃対象などを表示する
  - レベルを選ぶと数値が切り替わる。表示中のレベルはレベル別の一覧でも強調する
  - カードが複数のユニットを出す場合はユニットごとに分けて表示する
  - どの画面のカード画像からでも遷移できるよう、共通マクロ側でリンクにした。
    対戦履歴だけは行全体が既にリンクのため、リンクの入れ子を避けて対象外としている

**情報源の選定**

公式APIは性能値を提供していない（`/cards` は名前・レアリティ・コスト・画像・最大
レベルのみ）。稼働中のAPIに対し `/constants` `/cards/stats` など14種類の候補を
総当たりして確認済み。公式サイトにもカードデータベースは無い。

性能値はゲーム本体のデータファイルに入っているが、そこからの抽出は Supercell の
利用規約 §1.1 が明示的に禁じているため採用しない。

> "Reverse engineer, decompile, disassemble, decipher or otherwise attempt to derive
> the source code for any underlying software … or to obtain any information from the
> Service or any Supercell game using any method not expressly permitted by Supercell"

コミュニティの情報源を比較した結果、**Clash Royale Wiki（Fandom）** を採用した。

| 候補 | 判断 |
|---|---|
| RoyaleAPI / Deckshop | **不採用**。robots.txt が ClaudeBot 等のAIクローラーを `Disallow: /` とし、`Content-Signal: ai-train=no` を宣言している |
| cr-api-data | **不採用**。最終更新 2023-12-18 で約3年停止。新カード14枚が欠落し、既存カードもバランス調整前の値（ナイトのHPはLv.11換算で1790、現在は1766） |
| Clash Royale Wiki | **採用**。CC BY-SA で再利用が許諾され、公開MediaWiki APIで取得できる。122枚すべてのページが存在し、うち119枚から性能値を自動取得できた |

**実装上の要点**

- 取得は50件ずつのバッチで、**全122枚を3リクエスト**で済ませる
- 属性は種別ごとに列が違うため、列を決め打ちせず**ラベル駆動**で取り出す。
  wikiに新しい列が増えても表示は壊れない
- 性能値は `{{#vardefine: hp_11 | 1766 }}` の形でレベル11基準に格納されている。
  `golem_hp_11` のような接頭辞は、そのカードが出す別ユニットを指す
- 各レベルの値は `基準値 × 1.1^(レベル-11)` で算出する。wiki自身が各レベル表を
  作るのに使う式と同じにすることで、出典として示すページと表示が一致する
- CC BY-SA の義務として、出典・ライセンス・取得日・元ページへのリンクを画面に出す
- 自動取得できないカードは `src/data/card_stats_manual.json` で補う（現在1枚）

**ファイル数への影響**

カード詳細は絞り込みの組み合わせごとに複製せず、`<secret>/card/<id>.html` に1枚1
ファイルで置く。+122ファイルで、Cloudflare Pages 無料プランの上限20,000に対して
全体で901ファイル（4.5%）に収まる。

    （1回だけ当たる dmg／複数回当たる dmg×ヒット数／樽・配達系の spawn）
  - シールドを割ったダメージの余りは本体に届かない、という仕組みを再現する
  - 各レベルの値はサーバー側で算出して埋め込み、ブラウザでは比較だけを行う。
    JavaScript と Python で端数の丸め方が違うため、カードの性能ページと数値を揃える目的
  - 静的サイトでは `<secret>/spells/index.html` の1ファイルのみ

  - 墓石・ゴブリンの小屋・ゴブリンの檻・ゴブリンドリル・バーバリアンの小屋は、
    接頭辞付きの値が建物本体で、接頭辞なしの本体側が中から出るユニットを指す
    （他のカードと逆）。`SPAWNING_BUILDINGS` で補正する
  - 派生ユニットの空中・地上は元のカードと一致しないことがある（地上のダークネクロが
    出すコウモリは空中、空中のスケルトンバレルから落ちるスケルトンは地上）。
    `AIR_SUB_UNITS` で決める
- **修正**: 複数回当たる呪文のダメージが1ヒット分しか表示されていなかった。
  wiki と同じ「122×3（366）」の形にした
- **修正**: 出現時の範囲ダメージ（wiki の Spawn Damage）に「生成ユニットのダメージ」
  という誤ったラベルが付いていた

## 14. 確定した設計判断の一覧

| 論点 | 決定 |
|---|---|
| データ取得経路 | 公式API＋RoyaleAPIプロキシ経由 |
| 収集の自動化 | Windowsタスクスケジューラで1時間おきに実行 |
| 分析粒度 | カード単位（自デッキでのフィルタ付き）。アーキタイプはフェーズ2 |
| 自デッキの同一視 | 類似度で自動グループ化（既定: 8枚中6枚一致） |
| 対象モード | ラダー（トロフィーロード）とランク戦。加えて `deckSelection = collection` の対戦のみ集計 |
| User-Agent | 全リクエストに `clash-royale-battle-analyzer/1.0.0` を設定（Cloudflare対策・必須） |
| 分析項目 | 基本セット＋カードレベル差と勝敗の相関 |
| 対象プレイヤー | v1.1.0 で複数プレイヤーに対応。集計は常に1人に閉じる |
| 統計の扱い | 最低試合数20未満はグレー表示、全勝率にWilson信頼区間を付与 |
| カードレベル | ゲーム最大レベルをカードマスタから動的に導出し、ゲーム内表示と同じスケールへ正規化 |
| カード表示 | 画像＋日本語名。対応表JSONを同梱し、新カード追加時は手動更新（編集UI・略称検索は非対応） |
| 画面デザイン | 白基調のフラットなUI。色は勝敗の方向を示す用途に限定（実装後に調整予定） |
| 公開方式 | 静的サイトを無料ホスティングへ。サーバーは借りない |
| 公開範囲 | 推測困難なURL（32文字）。認証は設けない |
| カード画像 | 初回に一括ダウンロードしてローカル保存し、オフラインでも表示可能とする |
| 実装言語・UI | Python＋Flask＋Chart.jsによるローカルWebダッシュボード |
| エラー通知 | ログファイル＋ダッシュボード上部の収集ステータス表示 |
